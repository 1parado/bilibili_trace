# AI Agent 端到端开发工作流

本文定义从需求到发布的统一流程。任何 Agent 都必须按适用步骤执行，不允许只生成代码而跳过验证。

## 1. Understand
- 阅读 `AGENTS.md` 与相关文档。
- 浏览仓库结构、Git 状态、构建配置、依赖和已有实现。
- 将需求拆分为可验证的用户行为和验收标准。
- 识别隐私、数据迁移、兼容性、性能和权限风险。
- 若需求存在影响架构/数据语义的歧义，先提问，不自行猜测。

## 2. Plan
非平凡任务先写简短计划：
- 目标和不做的内容。
- 涉及文件与模块边界。
- 数据流/状态变化。
- 测试方案与边界用例。
- 风险、回滚和文档更新。

## 3. Implement
- 从最小可验证切片开始。
- 优先纯函数和明确类型，隔离 Android 平台 API。
- UI 遵循单向数据流，状态明确且可测试。
- 采集事件必须带来源与时间；推导结果必须有定义版本。
- 权限、网络或数据不可用时显式呈现状态，不用伪造数据填充 UI。
- 不为未来假想需求预先构建复杂框架。

## 4. Verify
按改动类型执行：
- Domain：单元测试覆盖正常、边界、异常与重复输入。
- Persistence：DAO/repository 测试；schema 变更要有 migration 测试。
- Compose：关键交互、空状态、错误状态和无障碍语义测试。
- Platform：给出实际设备测试矩阵；单元测试不能证明系统权限行为。
- Build：运行 Gradle unit tests、lint 和 debug build。
- Inspect：检查 diff、依赖变更、资源、日志、敏感信息和文档一致性。

官方 Compose 测试参考：[Android Developers — Compose testing](https://developer.android.com/develop/ui/compose/testing)。

## 5. Review
- 确认没有改变未授权的公共行为。
- 检查数据口径是否被混淆。
- 检查错误是否被吞掉、警告是否被无理由屏蔽。
- 检查是否引入不必要依赖、后端、遥测或模型调用。
- 确认所有声明与实际测试证据一致。

## 6. Deliver
PR / 最终说明必须包含：
- 问题、方案、实现范围和重要取舍。
- 测试命令及真实结果。
- 未验证的设备/系统行为。
- 隐私影响与数据迁移影响。
- 截图（仅在 UI 变化且可用时，且不得包含个人信息）。
- 后续任务和已知限制。

## 7. Long-running project discipline
- 将大功能拆为独立 PR，避免一个 PR 同时重构、加功能和改样式。
- 重要数据模型或架构决策写入 ADR。
- 每次迭代维护 roadmap 和验收状态。
- 不要将计划、模拟结果或未执行的测试写成已完成。
