# Android 数据采集可行性与隐私设计

## 1. 结论摘要

| 数据 | 预期可行性 | 能说明什么 | 主要限制 |
|---|---|---|---|
| B 站应用前台使用 | 中高，需设备验证 | 应用被系统观测为前台的时间区间 | 权限、系统版本、事件缺失和厂商后台限制 |
| 视频标题/UP 主识别 | 中低至中，实验性 | 当前界面中可访问的文本候选 | 页面结构、WebView/播放器、无障碍节点暴露程度 |
| 内容切换时间 | 中低至中 | 检测到 UI 内容变化的时间 | 节点变化不一定代表开始播放或持续观看 |
| 真实视频播放时长 | 低，不能默认承诺 | 通常无法仅凭应用前台事件精确获得 | 暂停、后台播放、切屏、倍速、跳转和注意力无法可靠推断 |
| 分享链接补录 | 高（分享入口本身） | 用户主动分享/记录了某个内容 | 不证明用户实际观看过 |
| 学习效果 | 无法自动直接观测 | 可记录用户笔记、复习和实践行为 | 行为记录不等于理解或掌握 |
| 平台关注状态/历史接口 | 不确定，逐项评估 | 取决于稳定、授权且可用的接口 | 非官方接口可能变化；账号凭证和平台条款风险 |

这些是设计阶段的可行性判断，不是已完成的兼容性测试。

## 2. UsageStatsManager：应用级使用时间

### 适合用途
- 读取系统记录的应用使用事件。
- 估算目标应用进入前台与离开前台的时间区间。
- 按天/周汇总应用级使用情况，并与系统设置中的统计结果做对照。

### 不适合用途
- 不能直接说明正在播放哪条视频。
- 不能证明用户在认真观看。
- 不能保证每一条前后台事件都实时送达或完整。
- 不应把应用前台时间直接标成视频播放时长。

### 实现注意事项
- 通过系统的 Usage Access 授权流程获取权限；不要尝试绕过权限。
- 对权限撤销、首次授权前无历史、设备重启、事件缺失和重复进行处理。
- 查询历史事件并重建最近时间窗口，避免只依赖实时回调。
- 对照 Android 系统设置中的目标应用使用统计，记录设备型号、系统版本、测试窗口和误差。
- 使用系统事件时间，而不是查询发生的时间，作为事件发生时间。
- 评估不同 Android API 版本和主要 OEM 的实际行为。

## 3. AccessibilityService：可选内容识别

### 可尝试的能力
- 监听用户在目标应用中操作时产生的无障碍事件。
- 遍历可访问节点，寻找与视频标题、创作者或页面内容相关的文本。
- 通过节点/文本状态变化检测可能的内容切换。
- 结合包名白名单、短时间去抖和内容候选置信度减少误识别。

### 不能保证的能力
- 不能保证每个页面都暴露标题和 UP 主。
- 无障碍节点变化不等于播放开始/停止。
- 不同播放器、WebView、横屏全屏页和版本更新可能导致识别失效。
- 屏幕上可见但不在无障碍节点树中的内容可能无法读取。
- 仅靠前台/界面文本无法可靠区分暂停、后台播放、画中画、自动连播或用户是否专注。

### 安全与隐私要求
- 独立功能开关；在启用前清楚说明采集字段、用途、局限和数据去向。
- 仅处理用户明确选择的目标应用；对其他应用的事件立即忽略。
- 不采集私信、评论输入框、密码、支付、账号设置等无关内容。
- 不保存完整屏幕文本或默认截图；优先保留标题、创作者、内容 ID、时间、来源和置信度。
- 不将无障碍服务用于自动点击、点赞、关注、评论或规避平台控制。
- 提供随时关闭服务的路径；关闭后立即停止新的内容识别。
- 上架前核对目标分发渠道的最新 Accessibility API 政策、披露和声明要求，不假定一定获批。

### 推荐实现策略
1. 首版先交付 UsageStats 与分享补录。
2. 建立独立的 accessibility adapter，不让领域层依赖 Android 节点类型。
3. 只支持明确的包名白名单和有限的候选字段。
4. 先在开发者自有设备上构造测试矩阵，保存人工标注结果用于计算覆盖率/准确率。
5. 识别失败时产生可解释的 UNKNOWN/UNRECOGNIZED 状态，不猜测标题。
6. 用户更正应能覆盖面向分析的规范化字段，但保留最小化的来源与更正记录。

## 4. 系统分享入口

- 注册对适当文本/URL 类型的系统分享 Intent。
- 尽量提取 URL，并规范化常见的 B 站视频链接格式。
- 解析失败时允许用户编辑标题、UP 主和主题。
- 分享行为和自动识别行为使用不同事件类型。
- 分享链接中的参数应做最小化处理；不保存无关追踪参数，除非有明确功能需要。

## 5. Bilibili 平台接口

- 不把未经确认的非官方接口作为核心能力依赖。
- 接入前需验证官方文档/服务条款、授权方式、稳定性、限流、隐私要求和维护成本。
- 不要求用户粘贴 Cookie，不存储账号密码或会话令牌。
- 不能因为某个接口能返回历史或关注信息，就声称能返回真实视频播放时长。
- 若未来支持平台接口，必须将其作为可独立关闭的 adapter，并在 UI 标记数据来源和时间。

## 6. 时间语义

UI 和导出必须区分：
- **应用使用时长**：目标应用在系统统计口径下的使用时间。
- **识别内容区间**：界面中识别到某内容状态的时间范围。
- **估算观看时长**：基于显式假设计算的估计值，需标明方法和置信度。
- **学习记录**：用户主动记录的笔记、复习或实践。

禁止将上述指标合并为一个“真实观看时间”。

## 7. 测试矩阵

至少覆盖：
- Android 不同 API 级别和主要 OEM。
- B 站首页、搜索、推荐流、视频页、全屏播放器、竖屏/横屏、WebView 页面。
- 播放、暂停、切换视频、返回、锁屏、画中画（若适用）、后台播放。
- 快速连续切换、应用崩溃、设备重启、权限撤销/恢复。
- 用户关闭无障碍但继续使用 Trace。
- 多个账号/隐私页面不应被采集（测试时只使用开发者自己的测试账号）。

## 8. 上线前核对

- 目标 Android 版本与权限说明。
- Google Play 或其他分发渠道的无障碍 API 规则及表单要求。
- 隐私政策、数据安全披露、数据删除与导出说明。
- 数据处理是否符合适用法律和平台条款。
- 所有能力说明与实际测试证据一致。
