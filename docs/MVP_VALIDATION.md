# MVP 验证计划

## 1. 验证目标

在大规模开发前验证三个风险：
1. 用户是否真的需要跨时间的行为分析，而非已有历史记录或屏幕时间功能。
2. Android 上应用级使用统计和视频内容识别能否达到可接受的可靠性。
3. 用户是否愿意授予必要权限，并在看到洞察后采取实际复盘行动。

本文中的数量与阈值均为实验设计目标，不代表已得到结果。

## 2. 阶段 A：问题访谈（3–5 天）

### 样本
招募 8–12 位经常使用 B 站的用户，优先覆盖学习/技术内容消费者、时间管理需求者和普通娱乐用户。

### 访谈原则
围绕最近发生的具体行为提问，避免“你会不会用这个产品”一类诱导问题。

### 访谈问题
- 最近一次你想回顾 B 站使用情况是什么时候？当时做了什么？
- 你目前如何知道自己花了多少时间？哪里不够用？
- 你最近一个月有没有因刷视频打断计划？能描述一次具体事件吗？
- 你想知道的是应用总时长、看过哪些主题、还是学习后的行动？请排序并说明原因。
- 你如何处理看过的学习视频？会做笔记、复习或实践吗？
- 对读取屏幕文字/无障碍权限的顾虑是什么？什么解释能帮助你做决定？
- 如果内容识别经常出错，你愿意手动纠正吗？可接受的频率是多少？
- 哪类信息绝不希望被记录或上传？

### 输出
- 访谈纪要（去标识化）。
- 痛点按频率、强度和当前替代方案排序。
- MVP 假设、反例和未解决问题。
- 不因礼貌性正面反馈直接判定需求成立。

## 3. 阶段 B：技术可行性 Spike（5–7 天）

### 必做
- 创建最小 Android 项目和 Room 数据库。
- 获取目标应用包名的 UsageStats 事件。
- 生成应用使用会话，并与系统设置统计对照。
- 建立本地事件时间线。
- 接收系统分享的 B 站链接并保存。
- 记录权限撤销、重启和缺失事件的行为。

### 可选实验
- 单独开发 AccessibilityService 原型。
- 在开发者自有设备、有限页面和自有测试账号上，采集视频标题/UP 主候选。
- 对每个测试样本做人工真值标注。
- 计算覆盖率、字段准确率、重复率和识别延迟。
- 评估耗电、权限解释和用户体验。

### 目标门槛（需要实测）
- 应用级每日时长与系统统计的误差目标 ≤5%，并记录无法解释的偏差。
- 人工标注样本中的内容切换识别覆盖率目标 ≥70%。
- 成功识别样本中的标题/创作者字段准确率目标 ≥95%。
- 重复事件率目标 ≤2%。
- 所有展示指标可追溯到事件或计算公式。

如识别指标未达到，不要用更多 AI 文案掩盖数据问题；缩小范围，优先交付应用级统计、分享补录与手动学习记录。

## 4. 阶段 C：可用性测试（3–5 天）

让 5 位左右用户完成：
- 开启应用级统计权限。
- 查看今日使用时长。
- 在 B 站中打开视频并检查识别结果（仅对自愿开启内容识别的用户）。
- 纠正一条错误内容。
- 分享一条视频给 Trace。
- 将一条内容加入学习目标并添加笔记。
- 导出或删除一条记录。

观察完成率、困惑点、权限理解和纠错成本；不要只收集满意度评分。

## 5. 阶段 D：两周试点

### 样本
目标 10–15 位自愿参与者。必须明确数据用途、保留期限、退出方式和权限范围。

### 观测指标
- 权限引导完成率。
- 7 天内至少 3 天有有效记录的比例。
- 每周时间线/周报使用频率。
- 识别纠错频率与每次纠错耗时。
- 看到洞察后实际采取的行动（例如新增复习、修改目标）。
- 用户是否关闭无障碍后继续使用应用级功能。
- 数据缺失、重复、崩溃和耗电投诉。

默认在本地分析试点数据；如果研究者需要收集遥测，必须另行征得同意并明确收集字段。尽量使用去标识化汇总，不收集参与者的原始视频标题或完整行为轨迹，除非研究确有必要且已明确授权。

## 6. 决策门槛

### 继续投入
- 多位用户反复提及同一核心问题。
- 用户能在实际使用中理解数据口径。
- 数据质量达标，且周报/时间线促成有价值的复盘动作。
- 权限负担没有使大多数目标用户放弃。

### 缩小范围
- 应用级时长稳定，但无障碍识别不稳定或授权阻力大。
- 用户主要重视学习复盘而非视频识别。
- 重点转为应用时长 + 分享补录 + 手动学习闭环。

### 暂停/重新定位
- 用户只把产品当作一次性统计工具，没有复用行为。
- 识别结果长期无法达到质量门槛。
- 关键价值依赖高风险或不稳定的平台接口。
- 用户对权限和数据处理的信任无法建立。

## 7. 交付物
- 去标识化访谈总结。
- 技术测试矩阵和原始计量口径。
- 识别质量报告。
- 可用性问题列表。
- MVP 继续/缩小/暂停决策记录。
