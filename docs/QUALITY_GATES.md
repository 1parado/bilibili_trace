# 工程质量门禁

## 1. PR 级门禁
每个代码 PR 都应通过：
1. Gradle 配置可解析。
2. 单元测试通过。
3. Android lint 通过；如有合理例外，需说明并精确抑制。
4. Debug APK 构建成功。
5. 相关文档与变更一致。
6. diff 中无凭据、个人数据、调试截图或无关文件。
7. PR 明确说明未覆盖的设备/系统测试。

CI 未配置或失败时，不能标记“全部检查通过”。必须报告缺失或失败原因。

## 2. 领域逻辑门禁
时间/事件逻辑必须覆盖适用场景：
- 重复和乱序事件。
- 重叠与相邻区间。
- 缺失开始/结束边界。
- 跨午夜、时区和夏令时变化。
- 设备重启和最近窗口重算。
- 权限被撤销或首次授权。
- 无数据、零事件、部分数据、未知和错误状态。
- 用户纠错、删除和重新计算。

所有时长计算使用统一单位，禁止通过 UI 文本解析来进行领域计算。

## 3. 数据和隐私门禁
- 默认离线，不新增隐式遥测。
- 每个采集字段有目的、来源、保留和删除语义。
- AccessibilityService 的功能必须可选、明确披露、可撤销。
- 不能将可见文本变化解释为真实播放或注意力。
- 远程模型/API 需独立审批和用户同意。
- 导出/删除需覆盖关联实体、缓存和派生汇总。
- 数据库迁移不能丢弃已有用户数据。

## 4. UI 门禁
- 明确加载、空、权限未授予、错误和部分数据状态。
- 不把 unknown/unavailable 显示为 0。
- 使用资源字符串；支持屏幕阅读器语义、动态字体和系统深浅色策略。
- 主要交互可由 UI 自动化测试验证。
- 设计语言保持浅色、克制、清晰，不使用紫色作为主品牌色。
- 任何演示数据都要明确标记为示例，不能混入真实统计。

## 5. Release 门禁
发布前必须：
- 在目标 API 级别和至少一台真实设备上测试核心流程。
- 验证权限授予/撤销、重启恢复、后台限制与电量影响。
- 对内容识别建立人工标注样本并报告覆盖率、字段准确率和重复率。
- 核对目标商店关于 Accessibility API、隐私披露和数据安全的最新政策。
- 验证导出、单条删除、范围删除和全部删除。
- 更新版本说明、已知限制、隐私文档和支持范围。
- 不将未经验证的估计时长标为真实观看时长。
